# 0008：界面改为审片台，批注交给 AI（D28，取代 D16）

日期：2026-10-29

## 背景

PLAN v0.3 根据用户要求加入了剪映式手动编辑（D16：「AI 编排 + 剪映式手动编辑，两种方式能力相同」），
阶段 B 因此按一个小剪映来规划：多轨时间线上的拖动、裁剪、分割、磁吸，变换手柄，什么都能改的属性面板。

阶段 B 做到一半时，用户提出：实际用法主要是 AI 生成操作、生成视频，界面上手动剪辑并不方便，界面的目的是什么？
讨论之后的结论：

- 人在这个流程里的主要动作是**看片和提意见**，偶尔动手微调。手动剪辑的界面最难做（交互细节多、容易出 bug），用得却最少。
- 用文字描述「第 12 秒那张卡片往上挪一点」很费劲，AI 也容易理解错；在画面上点一下就能得到准确的条目 ID 和时间点。
- 导出一次要几十秒，`preview --sheet` 又是静态图，所以浏览器里能拖动进度的实时预览是界面最不可替代的价值。
- 界面 agent 交来的第一版是照剪映做的英文 16:9 通用剪辑器（媒体、音频、特效、滤镜……），印证了按原范围做会偏离数据模型：
  本项目里动画是样式和模板的属性，叠加层按字幕锚定，不是时间线上的独立片段。

## 决定

1. **界面定位为审片台**（PLAN 第 10 节）：实时预览、点选、批注交给 AI、少量直接微调、撤销 / 锁定、导出。
   - 保留的直接操作：拖动画面元素的位置、叠加层出现时间「早一点 / 晚一点」、改字幕错别字、从样式库套用样式和动画预设、
     轨道锁定 / 隐藏 / 静音、撤销 / 重做。
   - 不做：时间线上的拖动剪辑、裁剪、分割、磁吸。这些写批注交给 AI。
     （2026-10-29 修订：移动、裁剪、分割、吸附加回界面，见 `0009-timeline-editing-and-hooks.md`。）
   - 数据模型、ops、渲染都不变；AI 通过 CLI / MCP 仍然能用全部功能。
2. **批注存在 `review.json`**，和 `project.json`、`editor.json` 并列：
   - 不放进 `project.json`：写批注不应该产生新版本，也不应该和 AI 正在做的修改发生 `CONFLICT`。
   - 不放进 `editor.json`：批注是人和 AI 之间的协作数据，要被 AI 读取，不是单纯的编辑器状态。
   - 和工程共用一把锁、原子写入（`node/store`）；格式见 `core/review.ts`（`version: 1`）。
   - 每条批注记下时间点 `atMs`、条目 `target`、画面位置 `point`，以及写批注时的工程版本 `revision`，
     AI 能看出这条意见针对的是哪一版。处理后 `resolution` 记下谁、什么时候、改了什么、处理后的版本。
   - 指向不存在的条目会返回 `NOT_FOUND`。
3. **接口**：
   - CLI：`mw comments`、`mw comment`、`mw resolve`。
   - MCP：`comments`（默认只列未处理的）、`resolve`（必须写 note；不打算改的也 resolve 并说明原因）。
     人写批注走界面，MCP 不提供写批注。
   - 本地服务：`GET/POST /api/comments`、`POST/DELETE /api/comments/:id`；批注变化推送 SSE `review` 事件。
     MCP 在另一个进程里写批注时，服务通过监听 `review.json` 发现变化。
   - `mw guide` 加一条规则：开始工作前先看 comments。
4. **拖动锚定元素时保留锚点**：`planDrag` 移动跟随字幕 / 片段的元素时，只调整 `offsetMs`，不再改成绝对毫秒。
   原来照剪映的行为写的，审片台上的「早一点 / 晚一点」之后，元素在剪切、变速时仍然要跟着那句话走。

## 影响

- 阶段 B 的范围和验收按 PLAN 第 11 节重写；第一项验收变成「点选 → 批注 → AI 通过 MCP 处理 → 界面刷新」的完整闭环。
- `core/edit.ts` 里的 `planDrag` 的裁剪部分和 `planSplit` 暂时没有界面调用，但保留：AI 和以后的文稿视图可能会用到，测试也在。
- 界面 agent 的第一版草稿移出了仓库（`../web-draft/`），按新范围在 `src/web` 重做，可以参考它的配色和布局比例。
